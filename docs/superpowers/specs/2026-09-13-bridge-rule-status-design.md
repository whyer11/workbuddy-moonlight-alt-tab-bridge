# Pad 桥接规则清单与实时状态设计

## 目标

在 Pad 端 WorkBuddy 桥接 App 首页集中展示当前已实现的键盘桥接规则，并同时区分“规则已配置”和“桥接链路正在运行”。用户无需回忆实现细节，即可判断每条规则做了什么、Pad 端是否工作、电脑端是否在线。

## 首批规则

首页固定展示以下三条规则：

1. Alt+Tab：物理键 `Alt+Tab` 在 Pad 端转换为 `Alt+F12`，电脑端恢复为 Windows `Alt+Tab`。
2. Windows 键：小米键盘 `Command/Left Meta` 在 Pad 端转换为 `Scroll Lock`，电脑端恢复为完整的 `Left Windows` 键。
3. 方向键：上、下、左、右键由 Pad 端虚拟键盘按原键值直通，电脑端无需二次恢复。

每条规则包含稳定 ID、名称、原始输入、Pad 端输出、Windows 最终动作、是否需要电脑端恢复。新增规则时必须向同一规则清单添加条目，页面不为单条规则编写专用布局。

## 页面结构

首页从上到下分为：

- 标题与整体链路状态。
- 当前 Shizuku/底层桥接状态说明。
- “授权并启动底层桥接”按钮。
- “桥接规则”列表。

每张规则卡展示转换链路，并显示两个相互独立的状态：

- 配置状态：`已配置`。表示当前安装版本包含该规则。
- 运行状态：分别显示 `Pad 端运行中/未运行` 与 `电脑端在线/离线`。方向键不需要电脑端恢复，因此显示 `电脑端无需桥接`。

整体状态按以下优先级生成：

1. Pad 底层桥接未运行：`Pad 端异常`。
2. Pad 正常，但任一需要电脑端恢复的规则无法确认电脑端：`电脑端离线`。
3. Pad 和电脑端均正常：`全链路正常`。

页面前台每两秒刷新一次，退到后台后停止轮询；恢复前台时立即刷新。离线仅影响状态显示，不停止现有按键桥接。

## Pad 端运行状态

现有 App 只知道 Shizuku UserService 的 Binder 已连接，无法确认原生桥接进程是否存活。BridgeUserService 将通过只读 Binder 状态接口返回：

- 原生桥接进程是否存活。
- 当前桥接协议版本。
- Pad 端已加载的规则 ID。

BridgeController 保存 Binder 引用并将结果转换为不可变页面状态。查询失败、Binder 断开或响应超时一律视为 Pad 端未运行，不影响 supervisor 原有的自动拉起逻辑。

## 电脑端实时状态协议

Windows Host 增加只读 UDP 状态响应，使用固定协议版本和固定端口。Pad 向用户配置的电脑 Tailscale 地址发送探测包；Host 仅返回：

- 协议版本。
- Host 版本。
- 当前支持的规则 ID。

协议不接受启动、停止、键盘注入或任意命令，不返回用户数据。响应必须带回探测请求中的随机 nonce，Pad 只接受来源地址、nonce 和协议版本均匹配的响应。

Windows 防火墙规则只允许 Tailscale CGNAT 地址段访问该 UDP 端口。若用户未配置电脑地址、Tailscale 不通、响应超时或协议不兼容，页面显示 `电脑端离线`，现有键盘桥接继续工作。

电脑地址保存于 App 私有配置。首次安装当前版本时预填本次部署检测到的电脑 Tailscale IPv4；页面提供可编辑入口，避免将某台电脑的地址写入公开仓库或 APK 源码。

## 兼容性与迁移

- 保留现有包名、Shizuku 授权、开机恢复和 native supervisor。
- 保留现有 Alt+F12 热键与 Scroll Lock 低级键盘钩子行为。
- 实时状态协议失败时只降级页面状态，不改变按键路径。
- Pad App、native bridge 与 Windows Host 版本分别展示，便于排查版本不一致。

## 测试与验收

开发采用测试先行：

1. 规则清单测试验证三条规则的稳定 ID、文案和电脑端需求标记。
2. 页面状态归约测试覆盖全链路正常、Pad 异常、电脑离线、方向键无需电脑端四种情况。
3. Binder 状态测试验证进程存活、断开和查询失败的降级行为。
4. Windows 协议测试先验证无响应，再验证合法请求、nonce 回显、未知请求拒绝和规则 ID 返回。
5. Pad UDP 客户端测试覆盖合法响应、错误 nonce、错误来源、超时和协议不兼容。
6. 回归现有 native remap、Windows Win 键集成测试和虚拟键盘设备能力测试。
7. 实机验证页面状态，并分别测试 Alt+Tab、Command+E、四个方向键。

验收完成后更新 README 与端到端验证记录，重新安装 Pad APK、替换 Windows Host、确认开机恢复，并将全部代码提交推送到现有 GitHub 私有仓库。
